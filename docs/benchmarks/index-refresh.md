# SQLite 来源变化后的索引刷新

SQLite 数据库或 WAL 变化时，原实现会重新读取受影响会话，并删除、重建每条会话的两份 FTS 正文。本次保留变化检测、完整读取和并发检查，在事务内比较原始标题与可搜索正文；内容相同且两份 FTS 行存在时，只更新状态签名、时间和处理计数。新内容和缺失的 FTS 行仍完整写入。

这减少了未变正文的分词、删除和插入，没有缩小来源读取范围，也没有假定 Session 时间戳一定随消息变化。

## 测量方法

- 基线为 `97183e383d46585f538ef35b0a2e6c6188723b0c` 的 release 行为；候选为本 PR。原始数据保存两份二进制 SHA-256。
- macOS arm64、Apple M1 Pro、Darwin 27.0.0、Rust 1.90.0；两份 CLI 使用 SQLite 3.53.2，fixture 使用 Python 3.11.15 / SQLite 3.50.4 创建。
- 分别查询 500、2,000 条 OpenCode V2 会话，每条 8 条消息、每条基础正文 1,024 字符。fixture 同时含 Codex 数据，但查询明确限制到 OpenCode。
- 每个场景各预热一次，再交错测量；500 条会话各 7 次，2,000 条各 5 次。不与构建、测试同时运行，不清空 OS 页缓存。
- 先用基线建立种子索引。热查询和刷新样本在每次执行前恢复同一份种子索引，避免前一个进程已刷新索引而造成虚假加速；新建索引场景每次删除索引。恢复及 fixture 构造不计时。
- 元数据场景只修改一条会话的 cost；消息场景只修改一条消息的 data。两者均保持所有 Session 创建、更新时间不变，并验证主数据库字节不变，变化只在 WAL 中。
- 每个样本验证成功状态、退出码、诊断和完整命中集合；两份二进制及重复样本的原始 stdout 字节必须相同，包括排名、分数、片段和元数据。读取前后全部持久源文件 hash 不变，覆盖数据库与 WAL，排除 SQLite 协调使用的 SHM。

## 结果

时间单位为毫秒，括号为最小值至最大值；RSS 是各样本峰值的中位数，单位 MiB。

| 500 条 SQLite 会话 | 基线时间 | 候选时间 | 基线 / 候选 RSS |
| --- | ---: | ---: | ---: |
| 新建索引 | 370.05 (358.05–404.24) | 366.14 (360.89–375.38) | 20.92 / 20.80 |
| 未变化的热索引 | 31.63 (30.02–33.22) | 31.23 (30.80–32.31) | 13.17 / 12.97 |
| 仅元数据变化 | 583.74 (566.11–615.75) | 138.33 (136.09–145.12) | 21.25 / 20.06 |
| 一条消息变化 | 576.00 (554.73–593.16) | 133.87 (129.49–175.42) | 21.33 / 19.88 |

| 2,000 条 SQLite 会话 | 基线时间 | 候选时间 | 基线 / 候选 RSS |
| --- | ---: | ---: | ---: |
| 新建索引 | 1489.88 (1482.42–1516.89) | 1480.74 (1462.81–1525.10) | 31.41 / 31.80 |
| 未变化的热索引 | 96.44 (94.20–98.77) | 98.04 (96.43–99.47) | 25.42 / 25.44 |
| 仅元数据变化 | 2450.01 (2373.88–2491.72) | 536.12 (523.83–563.17) | 32.59 / 31.94 |
| 一条消息变化 | 2368.79 (2333.29–2430.58) | 488.77 (477.74–494.49) | 30.83 / 29.58 |

刷新场景约快 4.2–4.8 倍；新建索引和未变化热索引的时间区间重叠。500 条会话的种子索引约 19.43 MiB，基线刷新后增至 25.04 MiB，候选保持 19.43 MiB；2,000 条分别为 75.00、95.62、75.00 MiB。这反映本轮写入后的文件增长，不表示候选会自动压缩已有索引。

本次使用重复性较高的合成文本，主要覆盖共享数据库变化而大部分正文未变的情况。所有正文都改变时仍须重建 FTS，且多一次比较；未测量该分布，不能声称任何更新场景都加速。其他 SQLite Provider 的 schema 解析成本也未单独测量。

## 验证与复现

行为测试覆盖状态刷新后不重复读取、标题和正文更新、两份 FTS 行分别缺失时的恢复，以及 DELETE / WAL 两种日志模式下消息变化但 Session 时间戳不变的搜索。原有慢读取竞争、删除竞争和事务回滚测试继续运行。

分别保存基线和本 PR 的 release 二进制后运行：

```bash
uv run python scripts/benchmark_index_refresh.py \
  --baseline /path/to/baseline --candidate /path/to/candidate \
  --sessions 500 --repeats 7 --output dist/benchmarks/index-refresh-500.json
uv run python scripts/benchmark_index_refresh.py \
  --baseline /path/to/baseline --candidate /path/to/candidate \
  --sessions 2000 --repeats 5 --output dist/benchmarks/index-refresh-2000.json
```
