# 读取批量并发验证

**决策：保留每批 32 个读取任务。** 比较 4、8、16、32 后，没有一个更小的批量在两类来源、两种规模及两个流程中稳定优于 32。较小批量会降低峰值 RSS，但部分耗时增加；本次不修改生产代码，不新增线程配置或自适应策略。

## 实验范围

- 基线 commit：`e4d280fa648db12eed9b3a88ad6c3e8daca1fa6c`，Rust 1.90.0 release，Apple M1 Pro（10 个逻辑核）、macOS arm64、Darwin 27.0.0。
- 四份二进制仅改变 `query/index.rs` 的 `pending.chunks(32)` 与 CLI `collect/sessions.rs` 的 `positions.chunks(32)` 中的批量值，其他源码相同。构建结束恢复原文件，二进制 SHA-256 保存在原始报告中。
- cold-index 执行 `--reindex`，每次先删除工具自己的索引和缓存。这里的“冷”指没有索引，不表示磁盘或操作系统页缓存为空。索引每批读取后提交一次事务，改变批量也会改变事务次数，测到的是完整流程，而不是单独的线程调度成本。
- collect 执行指定日期范围和 Provider 的 `--dry-run`，包含会话发现、正文读取、可见文本提取和完整分块规划；不调用 LLM，也不写报告。这里的读取批量与 collect 的模型请求 concurrency 配置不同。
- 每份二进制、每个场景预热一次，再测量八次；每轮轮换四个档位的执行顺序，让各档位在每个顺序位置各出现两次。不与构建或测试同时计时。
- 全部输入为临时目录内的合成 JSONL 或 SQLite，独立 HOME、Provider 根目录、缓存及导出路径。Source manifest 在测量前后必须一致，不访问真实会话。

输入复用 `benchmark_fixtures.py`，所有消息含英文、中文及唯一尾部标识：

| 数据组 | Codex 会话数 | OpenCode 会话数 | 普通会话消息数 | 每条普通消息基础字符数 | Codex 额外大消息 |
| --- | ---: | ---: | ---: | ---: | ---: |
| compact | 257 | 256 | 8 | 256 | 64 Ki 字符 |
| large | 513 | 512 | 20 | 2,048 | 1 Mi 字符 |

Codex 的最后一条会话只有 user、assistant 两条消息，其中 assistant 是表中的大消息；其余为普通会话。SQLite 全部为普通会话。JSONL 来源分别约 1.26 / 32.71 MiB，SQLite 约 1.19 / 40.80 MiB。

每次运行校验会话总数、退出码和完整标准输出、stderr（包含进度输出），并要求四个档位及重复样本完全一致。索引额外检查两份 FTS 表的完整身份、标题、正文摘要一致，原始正文逐条对照全部预期消息。仅不比较索引观察时间和物理数据库文件布局。collect 额外检查分块数非零且没有生成报告文件；其内容语义继续由现有 collect 回归测试保护。

## 峰值内存

下表为子进程峰值 RSS 中位数，单位 MiB；每次使用新计时进程的 `RUSAGE_CHILDREN`，不是进程树同时占用之和。

| 数据组 / 来源 / 流程 | 4 | 8 | 16 | 32 |
| --- | ---: | ---: | ---: | ---: |
| compact / JSONL / 建索引 | 13.26 | 13.78 | 13.91 | 14.98 |
| compact / JSONL / collect | 10.98 | 11.26 | 11.61 | 12.12 |
| compact / SQLite / 建索引 | 12.43 | 13.15 | 14.29 | 16.41 |
| compact / SQLite / collect | 12.31 | 13.02 | 14.16 | 15.89 |
| large / JSONL / 建索引 | 30.96 | 31.66 | 34.56 | 38.02 |
| large / JSONL / collect | 58.40 | 59.07 | 60.09 | 61.05 |
| large / SQLite / 建索引 | 17.31 | 20.09 | 23.04 | 28.75 |
| large / SQLite / collect | 49.65 | 51.54 | 53.72 | 56.20 |

以较大 SQLite 建索引为例，16 比 32 少约 5.71 MiB，耗时接近；但 compact SQLite 建索引中位耗时增加约 9%。降到 4 可以再节省内存，同时明显拖慢多数场景。在没有更严格内存约束的产品需求下，现有 32 是本次测量支持的折中，不证明它对所有机器、低速磁盘或所有 Provider 都最优。

## 复现

在基线 commit 上分别把两个 `.chunks(32)` 改为 4、8、16、32，每次执行 `cargo build --locked --release` 并把二进制复制到独立路径。恢复两处源码后执行：

```bash
uv run python scripts/benchmark_read_batches.py \
  --batch-4 /path/to/batch-4 --batch-8 /path/to/batch-8 \
  --batch-16 /path/to/batch-16 --batch-32 /path/to/batch-32 \
  --profiles compact large --repeats 8 \
  --output dist/benchmarks/read-batches.json
```

`--profiles smoke --repeats 1` 可快速校验基准入口。脚本 SHA-256：`a24fa252588565a81664803b8992bd958b4e7da9483a8ceb2b3b576bb2d68e7a`。
[完整原始数据](read-batches.json)保留全部 256 个计时样本、校验摘要和二进制摘要，仅规范化二进制路径。
