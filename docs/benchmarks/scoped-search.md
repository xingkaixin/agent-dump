# 搜索范围过滤优化

本次只减少搜索范围外的工作。空路径范围在打开索引前返回；非空范围仍刷新发现到的完整语料，保留全局 BM25 分数，再由 SQL 按 Provider 和会话 ID 过滤命中行。范围外的行不再计算 snippet 或参与结果排序。短词的字面搜索保持原实现。

## 测量方法

- 基线：`937794f99307769c26978d57e5c82c18c31b5aac` 的 Rust release 行为；候选：本 PR 的 release 构建。两份二进制 SHA-256 在原始数据中。
- macOS arm64、Apple M1 Pro、Darwin 27.0.0、Rust 1.90.0；两份 CLI 都使用 bundled SQLite 3.53.2。fixture 由 Python 3.11.15 / SQLite 3.50.4 创建。
- 1,001 条会话：501 条 Codex JSONL、500 条 OpenCode V2 SQLite，选择 11 条。4,001 条会话选择 41 条。普通会话各 8 条消息，每条基础正文 1,024 字符。
- 每场景每份二进制预热一次，再交错运行；小规模测量 7 次，大规模 5 次。计时包含独立 CLI 进程启动、发现、索引检查、查询和输出。
- 冷索引每次清空项目索引；热索引在计时外预建。未清空操作系统页缓存，不能解释为冷磁盘性能。测量期间不运行构建或测试。
- 每个样本检查完整 URI 集合、成功状态、退出码和诊断。两份二进制及所有重复样本的 stdout 必须逐字节相等，包括排序、分数、snippet 和元数据；空范围候选还检查索引文件没有创建。结束时校验全部 Provider 源文件 hash 未变。

## 查询计划的选择

直接加入 `f.rowid IN (...)` 的初版虽然加快窄范围查询，却使全范围从 409.94 ms 回退到 3044.80 ms，未采用该实现。使用与 CLI 相同的 SQLite 3.53.2 静态库，对生产 SQL 执行 `EXPLAIN QUERY PLAN`：

```text
f.rowid IN (...):  SCAN f VIRTUAL TABLE INDEX 0:=M4
+f.rowid IN (...): SCAN f VIRTUAL TABLE INDEX 0:M4
```

最终使用 `+f.rowid`，避免 rowid 成为 FTS 的逐键查询约束，保留全文匹配扫描后过滤。范围子查询通过 `(agent, session_id)` 唯一索引查找 rowid。SQLite 说明一元 `+` 可以排除 WHERE 项对索引选择的约束，同时也会移除类型亲和性；这里两端均为整数 rowid，并通过完整输出比较保护语义。这是针对已测回退的局部 workaround，升级 SQLite 时应重跑两个规模的全范围场景。[SQLite 查询优化器说明](https://www.sqlite.org/optoverview.html#disqualifying_where_clause_terms_using_unary_)
